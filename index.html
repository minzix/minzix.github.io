프로젝트 1

광고 데이터 적재 파이프라인 (인크로스 인턴)

개발 기간
2026.01 ~ 2026.02
참여 형태
팀원 7명 중 데이터 적재 담당 (네이버, 카카오모먼트)
  • Node.js
  • PySpark
  • Spark SQL
  • Apache Livy
  • Apache Iceberg
  • S3

서비스 내용

  • 네이버, 카카오모먼트 등 여러 광고 매체의 광고 데이터와 리포트를 하나의 저장소에 모아, 한곳에서 성과를 확인하게 하는 사내 통합광고플랫폼
  • 주요 기능: 매체별 메타 데이터, 리포트 데이터를 수집하여 Iceberg 테이블 통합 적재 (MERGE 기반 upsert)

배경 및 목표

  • 마케팅 담당자가 매일 약 3시간 정도씩을 소모하며 광고 매체마다 따로 접속해 성과를 확인하고 리포트를 직접 작성해야 했습니다.
  • 기존에는 광고 리포트를 RDB에 적재했는데, 리포트 데이터가 쌓이면서 하루치 적재에 약 4시간이 걸리게 됐습니다.

담당 역할

  • Spark 적재 파이프라인: Node.js 스크립트로 수집한 JSON을 Apache Livy REST API로 Spark 세션에 제출해 평탄화·컬럼 정규화한 뒤 Iceberg 테이블에 MERGE, 같은 데이터를 다시 올려도 행이 늘지 않도록 구성
  • 테이블별 머지 키 설계: 테이블마다 행을 유일하게 식별하는 최소 컬럼 조합 지정
  • 수집 방식 이원화: 잘 바뀌지 않는 메타 데이터는 ID 기준으로 최신 상태를 갱신하고, 매일 쌓이는 리포트 데이터는 날짜를 키에 포함해 일 단위로 누적 (둘 다 하루 1회 수집)
  • 필드별 전처리 기준: 공식 문서와 실제 응답을 대조해 각 필드가 어떤 광고 활동에서 발생한 값인지 확인
  • 팀 스터디: 처음 다루는 기술이라 팀원 2명과 1주일간 매일 Spark 스터디 진행

문제 해결 ① 하루치 리포트 적재 시간 (약 4시간 → 1시간대)

문제
리포트 데이터가 RDB에 누적될수록 하루치 적재 시간이 약 4시간까지 증가했습니다.
원인 분석
기존에는 Node.js 단일 프로세스가 매체 응답의 평탄화, 컬럼 정규화, 중복 제거를 순차로 처리한 뒤 RDB에 적재했습니다. 적재할 때마다 하나의 DB가 모든 행의 키 확인과 인덱스 갱신을 처리해야 해서, 누적 행이 늘수록 같은 하루치 데이터를 넣는 비용도 커졌습니다. 변환과 적재가 한 프로세스와 한 DB에 몰려 있어 처리 자원을 늘릴 수도 없었습니다.
해결 방법
변환과 적재를 Spark로 옮겼습니다. Node.js는 API 수집과 작업 제출만 맡고, 수집한 JSON을 Apache Livy REST API로 Spark 세션에 제출해 여러 Executor가 파티션 단위로 평탄화·정규화와 키별 최신 1건 선택을 처리하게 했습니다. 적재 대상은 S3의 Iceberg 테이블로 바꿔 MERGE로 upsert했습니다. 처음 다루는 기술이라 팀원 2명과 1주일간 매일 스터디를 진행해 학습 속도를 높였습니다.
결과
하루치 적재 시간이 약 4시간에서 1시간대로 줄었습니다. 누적 데이터에 비례해 늘던 적재 단계와 단일 프로세스에서 처리하던 변환 단계가 주로 줄었고, 매체 API 응답에 묶인 수집 시간은 그대로였습니다. 여러 매체를 따로 확인하던 업무를 하나의 플랫폼에서 처리하게 됐습니다.

문제 해결 ② 캠페인 유형과 무관한 지표 요청

문제
캠페인 유형과 관계없이 지표 그룹 12개를 모두 요청해, 빈 배열로 반환되는 데이터가 많았습니다.
원인 분석
공식 문서를 확인한 결과, 디스플레이 캠페인에는 메시지 지표 값이 존재하지 않고, 메시지 캠페인에는 기본, 추가, 동영상 지표 값이 없다는 점을 파악했습니다.
해결 방법
캠페인 상세 API에서 캠페인 유형(campaignType)을 먼저 확인해, DISPLAY면 MESSAGE, MESSAGE_ADDITION, MESSAGE_CLICK을, TALK_CHANNEL이면 BASIC, ADDITION, VIDEO를 빼고 요청했습니다.
결과
호출마다 요청하는 지표 그룹을 12개에서 9개로 줄여 25% 감소시켰습니다. 수집 단계로부터 필요한 데이터만 가져오도록 하여, 빈 응답에 대한 불필요한 파싱과 평탄화 과정도 함께 줄였습니다.

문제 해결 ③ JSON 평탄화 시 컬럼명 충돌

문제
광고 리포트 API의 중첩 JSON을 Spark DataFrame으로 평탄화하는 과정에서 서로 다른 경로의 필드가 동일한 컬럼명으로 변환되었습니다. 이 상태에서 Spark SQL 조회나 MERGE를 수행하면 어떤 컬럼을 참조해야 하는지 구분할 수 없어 AMBIGUOUS_REFERENCE 오류가 발생했습니다.
원인 분석
기존 평탄화 로직은 상위 객체 경로를 제거하고 마지막 필드명만 사용하는 리프 필드명 기반 평탄화 방식이었습니다. 이 때문에 원본 JSON에서는 서로 다른 객체에 속한 별개의 필드라도 마지막 필드명이 같으면 평탄화 이후 동일한 이름의 컬럼으로 생성되었습니다.
해결 방법
평탄화 시 생성되는 컬럼명을 검사해 중복 여부를 확인하고, 이름이 충돌하는 필드에는 상위 객체 경로를 반영하는 경로 보존형 평탄화 방식을 적용했습니다. 처음 등장한 필드는 기존 컬럼명을 그대로 유지하고, 같은 이름이 추가로 발생하는 필드에만 상위 경로를 접두어로 붙였습니다. 이를 통해 기존 컬럼명은 최대한 유지하면서도 충돌이 발생하는 컬럼은 원본 경로를 통해 구분할 수 있도록 했습니다.
결과
중첩 구조가 서로 다른 리포트에서도 컬럼명을 유일하게 유지할 수 있었고, AMBIGUOUS_REFERENCE로 인한 Spark 작업 실패를 제거했습니다. 또한 충돌 처리 로직을 공통 평탄화 단계에 적용해 리포트별로 개별 예외 처리를 추가하지 않고도 동일한 규칙으로 데이터를 변환할 수 있도록 개선했습니다.

문제 해결 ④ Livy statement 크기 한도 초과

문제
테이블의 payload가 73,361,596 bytes(약 70MB)로 statement 크기 한도를 넘어 업로드가 실패했습니다.
원인 분석
테이블 단위 데이터를 하나의 Livy statement 요청에 직렬화해 전달하고 있어, 데이터량이 증가하면 statement payload가 Livy/RPC 메시지 크기 제한을 초과하는 구조였습니다.
해결 방법
payload가 50MB를 넘으면 데이터를 나눠 여러 statement로 순차 제출했습니다.
결과
소재 23,092행, 광고세트 50,098행을 포함한 7개 테이블을 1분 34초에 적재했습니다.

회고

  • 데이터 엔지니어링은 데이터가 발생하는 비즈니스 맥락을 이해하는 데서 출발한다는 것을 배웠습니다.
  • 데이터가 지속적으로 증가하는 시스템에서는 현재 처리 시간을 줄이는 것뿐 아니라, 데이터 증가에 따라 병목이 어떻게 커지는지까지 고려해 처리 구조를 설계해야 한다는 것을 배웠습니다.
  • 외부 API의 데이터를 그대로 수집하기보다 공식 문서와 실제 응답을 함께 확인하고, 각 필드가 어떤 도메인 조건에서 발생하는지 이해해야 불필요한 요청과 잘못된 전처리를 줄일 수 있다는 것을 배웠습니다.

커머스 판매 데이터 동기화 워커 (인크로스 인턴)

개발 기간
2026.03 ~ 2026.06 (인크로스 플랫폼엔지니어링팀 인턴)
참여 형태
개발 및 운영
  • Node.js
  • axios
  • MySQL
  • PM2

서비스 내용

  • 커머스 플랫폼의 상품 데이터와 주문 데이터를 주기적으로 사내 DB에 동기화해, 마케팅팀이 사내 대시보드에서 판매 추이를 확인하게 하는 워커

배경 및 목표

  • 마케팅팀이 판매 추이를 확인하려고 커머스 플랫폼을 상시 직접 조회해야 했습니다.

담당 역할

  • 커머스 API 연동: 참조 관계에 맞춰 상품 → 주문 → 주문 상세 순서로 동기화
  • 운영: 동기화 JOB을 종류별로 분리하고 PM2로 운영
  • 커넥션 관리: 프로세스 시작 시 커넥션 풀을 만들고 모든 JOB이 풀에서 커넥션을 사용
  • 단계별 소요 시간 로깅: API 호출, 파싱, 테이블별 bulk insert, commit, 조회 시간을 나눠 기록
  • 성능 개선: 쿼리 처리를 트랜잭션으로 묶고, axios에 keep-alive agent를 적용해 TCP 연결 재사용

문제 해결 ① API 호출 한도 초과

문제
목록 API로 id와 메타데이터를 받은 뒤 id마다 상세 API를 호출해, 목록 길이만큼 호출이 필요했고 시간당 500회 한도를 자주 초과했습니다.
원인 분석
상세 정보가 필요 없는 id까지 모두 상세 API를 호출하고 있었습니다.
해결 방법
목록 응답의 메타데이터로 판별할 수 있는 불필요한 id를 SELECT로 먼저 걸러, 필요한 id만 상세 API를 호출했습니다. 예를 들어, 재고 개수가 0인 상품은 상세 정보(옵션, 가격)가 바뀌지 않아 기존 DB 값을 그대로 써도 됐고, 판매 이력은 주문 API로 따로 수집했습니다.
결과
호출량이 안정돼 시간당 500회 한도를 넘지 않게 됐습니다.

문제 해결 ② 고정 주기 실행으로 인한 작업 중첩

문제
API 호출 횟수를 최적화한 이후에도 호출 한도 초과가 지속적으로 발생했습니다. PM2 로그를 확인한 결과, 다음 수집 함수의 시작 로그가 이전 실행의 종료 로그보다 먼저 기록되는 경우를 발견했습니다.
원인 분석
각 수집 함수를 setInterval로 고정 주기마다 실행하도록 설정했지만, 날짜나 상품에 따라 데이터양이 달라 수집 시간이 실행 주기를 초과하는 경우가 있었습니다. 이때 이전 함수 실행이 끝나기 전에 같은 함수가 다시 실행되면서 작업이 중첩되었고, 이 과정에서 불필요한 API 호출이 발생해 호출 한도 초과로 이어졌습니다.
해결 방법
setInterval을 이용한 고정 주기 실행 대신, 각 함수의 실행이 종료된 시점에 setTimeout으로 다음 실행을 예약하도록 변경했습니다. 동일한 함수는 이전 실행이 끝난 뒤 다시 실행되도록 해 중첩을 방지하고, 서로 독립적인 함수는 병렬 실행을 유지해 전체 수집 처리량에 미치는 영향을 최소화했습니다.
결과
수집 시간이 1분을 초과하더라도 동일한 함수가 중첩 실행되지 않도록 개선했고, 작업 중첩으로 발생하던 불필요한 API 호출과 호출 한도 초과 문제를 해소했습니다. 동시에 서로 다른 수집 함수의 병렬 실행은 유지해 전체 처리량을 보존했습니다.

회고

  • 실행 시간이 일정하지 않은 작업은 고정 주기가 아니라 종료 시점을 기준으로 스케줄링해야 한다는 것을 배웠습니다.
  • 운영 중 문제는 단계별 소요 시간을 나눠 기록해야 어디가 병목인지 판단할 수 있다는 것을 배웠습니다.

프로젝트 3

Nexus - API 명세 협업 플랫폼

개발 기간
2026.01 ~ 2026.06 (숙명여자대학교 졸업프로젝트)
참여 형태
팀장 (Backend, AI 기능 전반 담당)
  • Java
  • Spring Boot
  • Spring AI
  • JPA
  • MySQL
  • Redis
  • Jackson
  • RestClient
  • SSE
  • MCP
  • k6

서비스 내용

  • 백엔드의 API 명세 변경을 자동 감지해, 프론트엔드가 변경을 모른 채 구현하다 통합 단계에서 깨지는 문제를 줄이는 협업 플랫폼
  • 주요 기능: Swagger 스냅샷 변경 감지(ADDED / REMOVED / MODIFIED), 개발 현황을 설명하는 RAG 챗봇(SSE 스트리밍), 외부 AI 용 MCP 서버

배경 및 목표

  • 팀 프로젝트마다 변경된 API 명세를 뒤늦게 확인해 연동 오류가 반복됐습니다.
  • Swagger 문서는 현재 상태만 보여줄 뿐 직전 대비 무엇이 바뀌었는지는 확인하기 어려워, 사람이 눈으로 대조해야 했습니다.

담당 역할

  • RAG 챗봇: 프로젝트 문서와 API 정보를 검색해 개발 현황을 설명하는 챗봇 구현
  • LLM-as-Judge 자동 평가: 선행 연구의 평가 기준을 참고해 검색 재현율과 생성 충실도를 분리해 평가하고, 품질 저하 원인이 검색 단계인지 생성 단계인지 구분할 수 있도록 평가 체계 설계

문제 해결 ① RAG 데이터 변경 시 검색 데이터 정합성 유지

문제
원본 데이터가 수정되거나 삭제된 뒤에도 이전에 생성된 청크가 Vector Store에 남아, 현재 데이터에는 없는 정보가 검색되고 챗봇이 이를 근거로 답변하는 문제가 발생했습니다. 또한 내용이 바뀌지 않은 데이터를 반복해서 처리하면 같은 데이터를 다시 임베딩하는 불필요한 작업이 발생할 수 있었습니다.
원인 분석
기존 방식은 새로 생성된 청크를 upsert하는 구조라, 원본 데이터의 변경 여부와 이전에 저장된 청크 상태를 함께 관리하기 어려웠습니다. 이 때문에 수정으로 사라진 청크나 삭제된 데이터가 Vector Store에 남을 수 있었습니다.
해결 방법
원본 데이터별 색인 관리 정보와 내용 변경 여부를 관리해, 실제 변경이 발생한 경우에만 다시 색인하도록 구성했습니다. 문서 수정으로 청크 수가 줄어들면 더 이상 존재하지 않는 이전 청크를 삭제하고, 데이터 삭제 시 관련 벡터와 색인 관리 정보도 함께 정리했습니다.
결과
변경되지 않은 데이터의 반복 임베딩을 줄이고, 수정으로 사라진 청크와 삭제된 데이터가 Vector Store에 남지 않도록 했습니다. 이를 통해 현재 원본 데이터와 RAG 검색 대상의 상태를 일치시키는 인덱싱 구조를 구성했습니다.

문제 해결 ② RAG 검색 품질과 생성 품질을 분리해 평가하기 어려운 문제

문제
챗봇의 최종 답변만 평가하면 필요한 근거를 검색하지 못한 것인지, 적절한 근거는 검색했지만 LLM이 답변 생성 과정에서 제대로 활용하지 못한 것인지 구분하기 어려웠습니다.
원인 분석
RAG의 최종 답변에는 검색 단계와 생성 단계의 결과가 함께 반영됩니다. 하나의 최종 점수만 확인하면 검색 품질 문제와 생성 품질 문제가 같은 실패로 보이기 때문에, 어느 단계를 개선해야 하는지 판단하기 어려웠습니다.
해결 방법
질문, 검색된 컨텍스트, 생성 답변을 별도 judgeClient에 전달하는 LLM-as-a-Judge 평가를 구현했습니다. 검색 품질은 컨텍스트가 질문에 필요한 정보를 포함하고 있는지, 검색된 청크가 답변에 유용한지를 기준으로 평가하고, 생성 품질은 답변이 검색 근거를 충실하게 사용하는지, 질문에 적절히 답하는지, 환각이나 모순이 있는지, 응답 지시를 준수하는지를 기준으로 평가했습니다. 총 7개 지표를 평가 기준과 함께 정의하고 JSON으로 반환받았으며, temperature=0.0으로 변동을 줄였습니다.
지표의미
검색 정보 충분성질문에 답하는 데 필요한 정보가 검색 결과에 얼마나 충분히 포함됐는지
검색 정보 적합성검색된 정보가 질문과 답변에 얼마나 관련 있고 유용한지
검색 정보 충실도답변이 검색 정보에 의해 얼마나 충실하게 뒷받침되는지
질문 답변 관련성답변이 사용자 질문의 의도와 핵심에 얼마나 직접적으로 대응하는지
시스템 지시 준수도한국어 응답, 원문 인용 등 지정한 응답 규칙을 얼마나 준수하는지
환각 정도검색 정보에 없거나 검색 정보로 뒷받침되지 않는 내용이 포함된 정도
검색 정보 모순 여부답변이 검색 정보와 명백하게 상충하는지 여부
결과
검색 품질이 낮은 사례와 검색 결과는 적절하지만 생성 품질이 낮은 사례를 분리해 확인할 수 있게 됐습니다. 이를 통해 검색 데이터와 검색 방식부터 개선해야 하는지, 생성 프롬프트와 답변 생성 단계를 개선해야 하는지 판단할 수 있는 평가 기준을 마련했습니다.

문제 해결 ③ Swagger 정보 동시 동기화 시 동일 스냅샷 중복 생성

동기화 과정
Swagger URL을 등록하면 먼저 명세의 변경 여부를 확인하기 위해 해당 URL에서 API 명세를 조회해서 spec_hash를 생성하고, 기존 최신 스냅샷의 해시와 비교합니다. 해시가 다르면 필요한 정보를 파싱 및 정규화해서 DB에 새로운 스냅샷으로 저장합니다.
문제
같은 팀에 Swagger 등록 요청 N개를 동시에 보내면, 동일한 spec_hash를 가진 스냅샷이 N개 생성됐습니다.
원인 분석
기존 로직은 최신 스냅샷의 해시를 확인한 뒤 새 해시와 비교하고, 값이 다르면 저장하는 구조였습니다. 하지만 해시 확인과 저장 사이에 동시성 제어가 없어 여러 요청이 다른 요청의 저장 결과가 반영되기 전에 동일한 최신 해시를 조회했고, 모두 새 스냅샷 생성이 필요하다고 판단했습니다.
해결 방법
팀 행에 PESSIMISTIC_WRITE 락을 적용해 같은 팀의 Swagger 동기화 요청을 순차 처리했습니다. 후속 요청은 선행 트랜잭션이 스냅샷 저장을 완료하고 커밋한 뒤 갱신된 최신 해시를 확인하므로, 동일한 spec_hash라면 스냅샷 생성을 건너뛰도록 했습니다.
결과
3회 반복하여 검증한 결과, 동시 요청 5개에서 생성되던 신규 스냅샷이 5개에서 1개로 줄어든 것을 확인했습니다.

문제 해결 ④ 태스크 목록 조회 지연

상황
TASK와 FLOW는 M:N 관계로, FLOW_TASK 매핑 테이블을 통해 연결 관계를 관리했습니다. 특정 팀의 태스크 목록과 각 태스크에 연결된 플로우 정보를 조회하는 API(이하 팀 태스크 목록 API)를 제공했습니다.
측정 환경
항목측정 환경
실행 환경로컬 Docker
CPU, 메모리 제한App 컨테이너 2 CPU, 2GB
MySQL 컨테이너 2 CPU, 2GB
테스트 데이터 규모약 240만 행
부하 테스트 도구k6
문제
팀 태스크 목록 API는 0.3 RPS에서도 p95 응답시간이 약 5.2초에 달했습니다. 부하를 0.8 RPS로 높이자 p95가 약 32초로 급증해, 초당 1회 미만의 요청에서도 포화 징후가 나타났습니다.
원인 분석
문제 API의 코드를 추적한 결과, 태스크마다 flow_task와 flow를 각각 조회하는 구조를 발견해 2N+1 쿼리 발생을 가설로 세웠습니다. Hibernate 실행 통계로 검증한 결과 태스크 79개에서 160개, 500개에서 1,002개의 쿼리가 실제로 실행됐습니다. 이어 EXPLAIN ANALYZE로 각 SQL문을 분석하며 flow_task의 기존 (flow_id, task_id) 복합 unique 인덱스가 task_id 단독 조회에 비효율적인 것도 확인했습니다. 부하 테스트에서 MySQL CPU가 약 97.7%까지 상승한 반면 App CPU는 낮게 유지돼, 반복 쿼리와 비효율적인 DB 조회를 주요 병목으로 판단했습니다.
해결 방법
태스크별 반복 조회를 IN 조건의 일괄 조회로 변경하고, 조회 결과를 메모리에서 태스크별로 합쳐 쿼리 수를 고정했습니다. 이어 flow_task(task_id), task(team_id), member_team(member_id) 인덱스를 추가해 조회 범위를 줄였습니다.
결과
개선 전후 코드를 이어서 측정한 결과, 태스크 목록 쿼리는 160개에서 4개로, p95는 5,158ms에서 45.3ms로 줄었습니다(−99%). 500개 태스크를 가진 팀에서도 쿼리 수가 1,002개에서 4개로 유지됐습니다. DB에 반복적으로 가해지던 조회 부하가 제거되면서 MySQL CPU 사용률도 57.5%에서 1.5%로 감소했습니다. 또한 500개 태스크를 가진 팀의 경우에도 0.2 RPS 기준 p95가 5,130.9ms에서 45.4ms로 감소해 약 99.1% 개선됐습니다. 이를 통해 일반적인 팀 규모에서 DB 병목을 완화했을 뿐 아니라, 태스크가 500개까지 늘어난 경우에도 쿼리 수와 응답시간이 안정적으로 유지돼 데이터 규모 증가에 따른 성능 저하를 크게 줄였음을 확인했습니다.
